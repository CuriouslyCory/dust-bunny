# The server credits a signed-in player's Run, once, through a ledger

A Run is credited when its Fluff and lifetime stats (`MetaProgress.awardRun`) are added to the player's progress. Until now, for a signed-in player, *who* credits a Run was decided by several separate client rules (ADR 0002, "Known limits"): the Account generation, waiting out this page's uploads, the take confirmation before an ending, the title read epoch, and the synced-copy rule. Each closed one race and together they left four open: a lost answer left a Run uncredited; an offline End run past the timeout trusted the device, so a Run could be credited on two devices; the server remembered only the last Run that ended; and an offline unpause racing another device's new Run dropped the Run uncredited.

Two problems were tangled: **authority** (may this Run be credited, and by whom) and **idempotency** (apply the credit exactly once to a progress copy). They are now separate:

- **Authority is the server's.** A `run_credits` row, unique per `(user_id, run_key)`, is the only thing that means "this Run is credited". It is written when the device holding the Run claims its ending (`POST /api/run-credit`), or when the server itself replaces or abandons a stored copy. Nothing on the client decides it any more. *Who holds* a Run is the server's too: a `run_holders` row per `(user_id, run_key)` outlives the one-per-Account slot, so a Run is checked against its own holder, not against whatever the slot happens to hold now.
- **Idempotency lives in the progress copy.** `creditedRuns`, the newest Run keys whose credit a copy holds, is a field of the device save and of the cloud save (`Progress`). It is written in the same update as the Fluff it accounts for and adopted together with it, so whichever copy wins the cloud save's whole-copy merge carries the right set. Any device may apply any ledger row; `awardRun` is a no-op for a key the copy already lists.

The client still computes the Fluff from the Run's stats (`fluffForRun`) and the cloud save still carries it. The server stores only `reason` and a bounded stats subset.

Players without an Account are unchanged: they credit locally (now keyed by Run key, so the results screen and the `runEnded` listener can't credit twice).

## Data model

```sql
CREATE TABLE IF NOT EXISTS run_credits (
  id          bigserial   PRIMARY KEY,
  user_id     text        NOT NULL REFERENCES "user" ("id") ON DELETE CASCADE,
  run_key     text        NOT NULL,
  lease       text,                 -- the lease the Run ended under (the replaced copy's, for a replace)
  reason      text        NOT NULL CHECK (reason IN ('died', 'victory', 'quit')),
  stats       jsonb       NOT NULL, -- CreditStats (src/shared/runCredit.ts)
  credited_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (user_id, run_key)
);
CREATE INDEX IF NOT EXISTS run_credits_user_idx ON run_credits (user_id, id DESC);
ALTER TABLE player_progress ADD COLUMN IF NOT EXISTS credited_runs jsonb;  -- NULL: a row from before the ledger

CREATE TABLE IF NOT EXISTS run_holders (
  user_id    text        NOT NULL REFERENCES "user" ("id") ON DELETE CASCADE,
  run_key    text        NOT NULL,
  lease      text        NOT NULL,   -- the lease the Run was last stored or taken under
  ended_at   timestamptz,            -- set once the Run is over (an end, a claim, a replace of its stored copy)
  updated_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, run_key)
);
CREATE INDEX IF NOT EXISTS run_holders_user_updated_idx ON run_holders (user_id, updated_at DESC);
```

Applied lazily by `ensureSchema` (`server/schema.ts`; the probe checks `run_credits`, `run_holders`, their indexes and `credited_runs`) and mirrored in `db/schema.sql`. `saved_runs.ended_at` stays, for clients from before the ledger; the new path treats "ended" as "in the ledger" first, then as the holder record's `ended_at`.

**Holders.** `saved_runs` is one slot per Account, so it only remembers the last Run stored: once device A's new Run Y replaces X there, the slot no longer knows that device B is playing X. `run_holders` does. PUT (a store) and the take write the Run's current lease; the claim, DELETE and a replace of a stored copy set `ended_at`. A PUT or a claim for X is checked against X's own holder first: `ended_at` set → `409 run_ended`; a lease that is neither the caller's `lease` nor `prevLease` → `409 carried_on`; no row → the server never saw X, so nobody else can hold it. The slot's own lease and `ended_at` are checked second, for rows from before `run_holders` existed. The take needs the snapshot, which only the slot has, so it is unchanged apart from refusing a Run in the ledger. A DELETE for a Run the slot no longer holds but whose holder is the caller's answers `deleted: true` (the Run was theirs to end).

*Retention.* On every store, claim and end the Account's holder rows older than `HOLDER_RETENTION_DAYS` (90) or past the newest `HOLDER_KEEP` (200) are pruned (`pruneHolders`, `server/runCredits.ts`; a player who never pauses only ever claims, so the claim prunes too). A pruned Run reads as "never seen", which only matters for a device more than 90 days (or 200 Runs) behind: its claim for a Run that is in the ledger still gets the ledger row, and one for a Run that was ended by an old client (no ledger row) could be credited once more. Accepted.

*Bounds on the ledger.* A signed-in player can send a claim for any fresh `runKey`, and a never-seen Run is credited, so without a bound one Account could grow `run_credits` and `run_holders` without limit. Two bounds, both in `server/runCredits.ts`: a claim that would *create* a row is refused with `429 rate_limited` (and `Retry-After`) once the Account created `CREDIT_RATE_LIMIT.max` (30) rows in the last `windowSec` (600), the same allowance per Account as the leaderboard's Run board (a Run credits once as it posts once); the check runs after the row lookup, so a retry for a Run already in the ledger is answered from its row whatever the rate, and before any write, so a refused claim leaves nothing behind. The client treats a 429 like a network error: the claim stays in its durable queue and is retried with backoff (the results screen keeps reading pending). And the ledger keeps only the newest `CREDIT_KEEP` (1000) rows per Account (`pruneCredits`, run when a row is inserted, by a claim or a replace). A pruned row only matters for a claim more than 1000 Runs behind, by when the Run's holder record is pruned too (above): such a claim could credit the Run once more, within the limit already accepted for holders. The 100 remembered keys against 20 fetched are unaffected.

**Serialisation.** Every write (PUT, take, DELETE, claim) runs in a transaction that first takes `pg_advisory_xact_lock(hashtext('account_runs'), hashtext(user_id))` (`lockAccountRuns`). A row lock could not do this: a PUT into an empty slot and a claim for the same Run (the pagehide flush sends them together) found no row to lock and both decided. The take also carries `NOT EXISTS (… run_credits …)`, so a Run in the ledger is never handed out even to a client that skips the lock path.

`CreditStats` is what crediting reads: `maxRadius`, `debrisAbsorbed`, `tierReached` (required, bounded), and if present `characterId`, `difficulty`, `area`, the `*Cleared` flags that are true, and `areas` (≤ 16 of `{ area, radiusIn, maxRadius, debrisAbsorbed, cleared }`). Radii are real centimetres, so `CREDIT_STATS_BOUNDS.radius` is `PROGRESS_BOUNDS.bestRadius` (the last tier start, 2.8e25, times ten): a Universe Run must pass. `pickCreditStats` takes the subset out of a full `RunStats` or a stored snapshot's `stats`; a claim whose stats lack the three numbers, or exceed a bound, is a 400. `salvageCreditStats` is the server's last resort for a stored copy it credits on its own (a replace): each number is kept where it reads (clamped), 0 where it doesn't, Areas that read are kept; zeros for all three only when the copy has no stats at all. The client never needs it: a Run's own stats always pass `pickCreditStats`, and a client must not substitute zeros for stats it could not pick (that would credit a real Run as nothing); it sends the stats it has and treats a 400 as a bug to surface, not a credit of 0.

## API

**`POST /api/run-credit`** body `{ runKey, lease, prevLease?, reason: 'died' | 'victory' | 'quit', stats }` (≤ 8 KB)
- `200 { credit: RunCredit, created: boolean }` with `RunCredit = { id, runKey, reason, stats, creditedAt }`.
- `409 carried_on`: `runKey`'s holder record (or, for a Run from before holders, the slot) has it under a lease that is neither `lease` nor `prevLease`, and it hasn't ended. Nothing is written. The client: the Run is another device's; apply nothing, show "carried on on another device".
- `429 rate_limited`: the claim would create a row past the Account's allowance (above); `Retry-After` says when to try again. Nothing is written.
- `409 run_ended`: `runKey` ended but the ledger has no row for it. A client from before the ledger ended it (DELETE), or replaced its stored copy without `ledger: true`, and credited it itself; so it is **already credited elsewhere**: the client applies nothing, drops the claim, and must not retry it. The body is the usual `{ error: 'run_ended', message }`; no extra field distinguishes the two origins because the client's answer is the same for both. Nothing is written.
- 400 `invalid`, 401, 405, 413, 503 as the other functions.

Under the Account's advisory lock: a ledger row for `runKey` already there is returned, `created: false`, whatever the lease and whoever asks (a retry after a lost answer, or another device's claim for a Run already credited). Otherwise the Run's holder record is checked (above), then the slot: if it holds `runKey` under the caller's lease it is marked ended (snapshot cleared, `ended_at`), as DELETE did. If the slot holds another Run, or none, and the holder record allows it, the Run is credited and recorded as the ended Run on an empty slot (a Run still going in the slot is left alone), as DELETE did. The holder record is marked ended and the ledger row inserted. A claim is therefore safe to send any number of times, from any device.

**`GET /api/run-credit?limit=20`** → `200 { credits: RunCredit[] }`, newest first, at most 50.

**`PUT /api/saved-run`** gains `ledger?: boolean` and `credits: RunCredit[]` in its 200 answer:
- A `runKey` in the ledger is refused with `409 run_ended`, whatever the row holds now.
- A `runKey` whose holder record says ended is refused with `409 run_ended`; one another device holds (holder record or slot) with `409 carried_on`.
- With `ledger: true`, replacing a different stored Run records that Run in the ledger as a quit, with its stored snapshot's stats (`pickCreditStats`, else `salvageCreditStats`), in the same transaction; the row comes back in `credits` (and still in `replaced`). Without the flag nothing is recorded in the ledger and the caller credits `replaced` itself, as before. Either way the replaced Run's holder record is marked ended, so a later claim for it by a ledger client answers `run_ended` (already credited elsewhere) rather than crediting it again, and the sweep never sees it (it has no ledger row).
- The stored Run's holder record is written with the caller's lease.

`DELETE /api/saved-run` is no longer used by ledger clients. It marks the Run's holder record ended (the old client credits a `deleted: true` Run itself, so that mark is what later turns a ledger client's claim into `run_ended`), and it answers `deleted: true` for a Run the caller holds by its record even when the slot has moved on. `TODO(adr-0003)`: once every client sends `ledger`, drop `replaced` crediting and DELETE.

**`PUT /api/progress`** stores `creditedRuns` with the copy; a body without it keeps the stored set (like `loadouts`; this is also what a device whose set is unknown sends, below), and a row without one leaves it out of the answer.

### The `ledger: true` flag, and deploys

Vercel swaps the build under open tabs (ADR 0001). A tab from before the ledger credits a replaced Run from `replaced`, locally; if the server also wrote a ledger row for it, a new tab's sweep would credit it again. So the server writes a ledger row on a replace only when the uploading client says it credits through the ledger. Old tabs never claim, so their ended Runs never reach the ledger either. What they do leave is the holder record's `ended_at`: a new tab holding a stale synced copy of such a Run gets `409 run_ended` for its claim, not a second credit, however many Runs have passed through the slot since.

## The client (the spec for src/meta)

**`awardRun(e: { runKey: string; reason: RunEndReason; stats: CreditStats }, opts?: { ledger?: boolean; countUniverse?: boolean }): RunAward | null`** returns null when `runKey` is already credited: in `creditedRuns`, or in the device's record of credits with no Account (below). The check and the write happen inside one `store.update`, so two tabs applying the same credit (SaveStore read-modify-write, #51) can't both add it. `creditedRuns` keeps the newest `CREDITED_RUNS_MAX` (100) keys, and only keys the Account's ledger has or will get a row for (`ledger: true`, the default): a Run credited with no Account (`ledger: false`) is remembered on the device only (`local` in the mirror, below), so a hundred signed-out Runs can't push a ledger key out of the set while the ledger still returns its row. **A key whose claim is still out is never evicted.** A never-seen Run is credited on the device before its claim goes out (below), so its Fluff sits in the copy under its key; were a hundred more such Runs to age the key out while the claim waits (offline, or behind the server's rate limit), the answer would credit the Run again. So the claim queue is the source of truth for which keys are pending (`MetaProgress.pinCreditedRuns`, registered by `RunCreditQueue` with every claim in its file, any Account's), and a write of the set keeps the newest 100 keys *plus* any older pinned one (`trimCreditedRuns`): the set exceeds the cap only by keys claims are out for, and only until they land. Neither the sanitiser nor the mirror cuts the set back (the pins aren't known when the save is read at load; the next write trims). An adopt still replaces the set whole, pinned keys included, so a credit the adopted copy lacks is restored by the answer, once. The server accepts at most 100 keys, and a copy uploaded without a pinned key could be adopted by another device with that Run's Fluff and credited again from the sweep, so the cloud save does not upload while the set (trimmed as a write would leave it) is over the cap: the copy stays dirty, the status reads `syncing`, and the retry sends the newest 100 once the claims have landed (by then those rows are older than the 20 the sweep fetches). `SaveData.creditedRuns: string[]` is additive (sanitised default `[]`, no `SAVE_VERSION` bump); `Progress.creditedRuns?` likewise, missing meaning unknown. `progressOf` includes it; `adopt` copies it in the same update as `fluff` and `stats` (`MetaProgress.adoptCreditedRuns`, which keeps the mirror in step). The `awarded` WeakMap goes.

**Builds from before the ledger on the same device.** Vercel swaps the build under open tabs (ADR 0001), and an older tab's sanitiser drops save fields it doesn't know: its next write (a purchase, its own `awardRun`, an adopt) rewrites the save *without* `creditedRuns` but with the Fluff. Read back alone, that save would say the copy holds no credit, and the next sweep would add up to 20 rows' Fluff a second time. So the client keeps a device-side mirror, `dust-bunny:credited-runs:v1` = `{ version: 1, keys, local }` (`src/meta/creditedRuns.ts`), a key old builds never write: `keys` is `creditedRuns` as this build last wrote it (every `awardRun` and `adopt`), and a save read from storage (at load, and on another tab's write) that lacks mirrored keys gets them back before anything reads it (`SaveStore`'s `repair` hook); its Fluff is left alone. The rule is **losing the field must never create Fluff**: a key the save lost comes back without its Fluff (the copy may hold it or not), so the worst case is a credit not re-applied, never one applied twice. The mirror follows the copy: an adopt replaces `keys` with the adopted set (so what the adopted copy lacks is what the sweep may bring back, the merge-loss repair), another Account's save loaded (`replace`) starts it empty, and a mirror from a newer build is read but never written. The option of a sweep high-water mark (the newest ledger id reconciled) was not taken: it would also skip rows a merge legitimately dropped below the mark, and the mirror answers the question the sweep actually asks (is this key credited in this copy?).

The mirror only knows the keys *this device* wrote, though. An old-build tab can adopt a cloud copy that already holds another device's credit K2 (its Fluff, its key) and then rewrite the save without the field: the mirror never saw K2, so the repair can't bring it back, and the sweep would apply K2's row to Fluff that already holds it. So a save read with no `creditedRuns` field at all (not an empty one: this build always writes the field) on a device whose mirror exists (it has used the ledger; a save from before the ledger on a device without one is just an older save) marks the set **unknown** (`unknown` in the mirror, `MetaProgress.creditedRunsKnown`), which outlives reloads and this build's own writes. While it is unknown: the sweep does not run; the cloud save uploads the copy *without* `creditedRuns`, so the server keeps its stored set rather than taking an empty one; and a claim answered with a row that already existed (`created: false`) is not applied (some copy applied it, maybe this one), while one the claim created is. Credits this device applies meanwhile still add their key (the set is "at least these"). It becomes known again when a cloud adopt brings a copy that carries `creditedRuns` (including the server's copy of this same progress, when the two are equal in everything else), or another Account's save is loaded (`replace`, an empty set).

**Universes.** `universes` is max-merged between copies (the cloud save keeps the larger count, and so does the server), so a count can outlive the key that produced it: a device that counted a Universe victory and then adopts a copy without that key keeps the count and loses the key, and the sweep would count the victory again. So a ledger row that reaches a copy by the **sweep or an upload's `credits`** credits Fluff and stats only (`countUniverse: false`); a Universe is counted once, by the device that ended the Run (its local credit, or the answer to its own durable claim, `countUniverse: true`), and the merge carries the count to every other copy. The sweep leaves a row whose Run this device's own claim is still out for to that claim's answer, so a lost answer can't turn the player's own victory into a Fluff-only row. A claim for a Run that was credited on the device *before* it went out (the server never saw the Run, below) is marked `local`: its answer applies the row only when a later adopt dropped the key (Fluff and stats, so the copy that lost them gets them back), and never counts the Universe again, since the count was max-merged across that adopt.

**Who credits, and when the player sees Fluff.**
- Signed out: locally, at once.
- Signed in, Run the server was never told about (no upload or take was ever queued for it from this device while signed in, or it is `localOnly`): locally, at once, *and* a claim is recorded (its answer is then a no-op). Sound because no other device can hold a Run the server never saw. This is the common Run. "Ever queued" is remembered durably (`dust-bunny:known-runs:v1`, the newest 20 keys, `AccountRuns.knows`), not in the page's `live` state: signing out and back in mid-Run, or a reload, must not make a known Run look like one the server never saw and credit it on the device's word. The leases the server may hold the Run under are remembered with the key (written when an upload or take is queued, and again as a take or an upload moves them), so the claim for a known Run whose `live` state is gone still names the holder's lease; a fresh one would be refused as `carried_on` and the Run credited nowhere. A record without leases (an earlier shape of the file) falls back to the device slot's tag, as `creditQuit` does.
- Signed in, Run the server knows: deferred to the server's answer. The results screen does not block: it renders `+X Fluff` at once from `fluffForRun` over the same picked stats the claim sends (`creditStatsOf`), marked pending while the claim is outstanding, and updates the total when the credit lands (`fluffAwarded` gains `pending: boolean`; it fires again with `pending: false`). Online that is usually under a second; offline it reads "added when you're back online". Provisional crediting with a later revoke was rejected: it would subtract Fluff possibly spent and lower `totalFluffEarned`, which also flips the cloud merge.
- The claim's stats are the Run's own, bounded (`pickCreditStats`; a real Run's always pass), falling back to `salvageCreditStats` only for a stored copy with broken stats: never zeros for a Run. A `400` is therefore a bug on this side: it is logged with `console.error`, the claim is dropped, and nothing is credited; it is still a definite answer (`refused: 'rejected'`): the results screen reads "Not added: something went wrong on this side." and the Run board entry posts (the Run ended here).
- The device slot's replace (pause, Save & quit over another Run), New run's abandon, and the title's "server copy wins" branch all become claims with `reason: 'quit'` for a signed-in Account copy. The server's answer credits or refuses.

**The durable claim queue** (`src/meta/runCredits.ts`, key `dust-bunny:run-credits:v1`): `{ version: 1, claims: PendingClaim[], settled: SettledClaim[] }`, `PendingClaim = { userId, runKey, lease, prevLease?, reason, stats, at, local? }`, `SettledClaim = { userId, runKey, reason, fluff, outcome, at }` (the newest 20 answers, for the other tabs). A claim is written before its request goes out and removed on a definite answer (200 or 409); it is replayed on page load, when the browser comes back online, after an Account switch to its `userId`, and flushed with `keepalive` on `pagehide`. Claims for another Account wait. A newer `version` is left untouched (ADR 0001). Two tabs replaying one claim is harmless (the server returns one row; `creditedRuns` applies it once). The answers:
- `200`: the row is applied (`own`, so a Universe victory counts). A row this build can't read is applied from the claim's own stats (the server credited it all the same); the queue never blocks on it.
- `409 carried_on`: another device holds the Run. The claim is dropped, nothing is applied or shown as lost; the holder credits the Run when it ends, and the sweep brings the row here.
- `409 run_ended`: a client from before the ledger ended the Run, or replaced its stored copy, and credited it itself. Already credited elsewhere: the claim is dropped and never retried, nothing is applied. The results screen reads "Already added on another device", not "carried on".
- An answer that arrives after the Account changed (`gen`) is nobody's to apply: the claim *stays* in the file for its Account and goes out again when it signs in (a claim is safe to repeat). The queue then pumps the Account signed in now, which may have been waiting on that request.

Every definite answer is announced to the page (`onCredit`), not only one that adds Fluff: a 200 whose row the copy already holds (`already`: another tab applied the answer first, or the device credited the Run before the claim) and a 400 (`refused: 'rejected'`) settle the results screen and the leaderboard's wait like a credit or a 409 do, so neither waits on a claim that is gone. The outcome is also written to the file (`settled`) in the same write that removes the claim, and a tab hears the `storage` event for the queue key: a claim it was waiting on that is gone from the file is announced here with the recorded outcome (`already` for a credit: the other tab's `awardRun` wrote it into the shared copy), or, with no record (a tab of another build), as `already` when the copy holds the key. A Run's outcome is announced once per claim; a credit applied (an award) always is.

**The sweep** applies ledger rows the copy missed (a lost answer to a replace; another device's replace; a Run the merge dropped): `GET /api/run-credit` (20 newest), apply each row whose key is not in `creditedRuns` (Fluff and stats; not a Universe, see above), leaving a row this device's own claim is still out for to that claim. It runs from `syncTitle` after this page's work has settled, and after the queue drains following a network error, and not at all while the copy's set is unknown (above). 100 remembered against 20 fetched keeps a once-applied row from being applied again after its key aged out; that ratio holds because only ledger keys take the 100 slots.

**With the cloud save's merge.** The merge replaces a whole copy (the one with more `totalFluffEarned` wins). Double counting would need a copy holding a credit's Fluff without its key, which `awardRun` and `adopt` make impossible by writing both together. The reverse is a gain: today two devices crediting different Runs offline lose the loser's Run in the merge; now its ledger row is missing from the winning copy's `creditedRuns`, so the next sweep applies it.

**Redundant rules to delete:** `confirmHeld`, `unconfirmed`, `lostKeys`, `gateRunEnding`, `Run.endGate` and its gate in `Run.end`, the "Checking your Run…" toast, the `confirmHeld` step in `Game.endRun` (the cross-tab `handoff.takeBack()` stays), `creditsReplacedOnDevice`, `creditsOnServer`, the branching in `abandonSavedRun`, `prevLocalKey`, the `end` Op and its `credit`, the `replaced` crediting in `send` (apply the answer's `credits` instead), the `awardRun` branch in `syncTitle`, `SavedRunApi.end`, `MetaProgress.awarded`. `gen`, `titleEpoch`, `settledTag`, the `synced` tag and `lose()` stay: they decide who *plays* a Run and what the slot mirrors, not credit.

## The four races

1. **A lost answer.** The replace or abandon already wrote the ledger row; the device's durable claim, or the next sweep, gets the same row and applies it. Closed.
2. **Offline End run past the timeout.** No timeout and no device's word: the claim waits for the server, which checks the lease. A Run another device took is refused and not credited here. Closed; Fluff is deferred while offline.
3. **Only the last ended Run remembered.** PUT consults the ledger, so a late upload of A is refused whatever the row holds. Closed.
4. **Offline unpause vs another device's new Run.** B's upload replaces A's stored copy and records A as a quit; A's take is refused on reconnect and it steps aside (what it played since unpausing is still lost, as ADR 0002 accepts), but A's Run is credited once, by the sweep, rather than dropped. Closed as "credited, not dropped".

## Considered options

- **The server applies the credit to `player_progress` itself.** Rejected: it needs `fluffForRun` on the server, a row that may not exist yet (a device signing in with local progress would then win the merge and drop the credit), and Fluff would arrive by the sync round-trip rather than at once.
- **Award provisionally, reconcile later.** Rejected (above): revoking is lossy and fights the merge.
- **A server-side "applied" mark instead of `creditedRuns`.** Rejected: an ack can be lost like any answer, and the mark must travel with the copy the credit went into, which only a field in the copy does.
- **An id cursor in `Progress` instead of the 100/20 ratio.** Rejected for now: a claim applied directly can't advance a cursor past rows it never fetched.

## Consequences

- A paused-then-finished Run's Fluff, for a signed-in player, is confirmed by the server; offline it is shown as pending and lands on reconnect. Every other Run is credited at once as before.
- The ledger is a complete history of credited Runs per Account, so a device that falls behind by any number of Runs is refused, not just by one.
- The save and the cloud save grow by at most ~4 KB (`creditedRuns`).
- The leaderboard's Run board entry for a known Run waits for the credit (`src/ui/leaderboard/posting.ts`): `leaderboard_scores_run_idx` is unique on `run_id` with DO NOTHING, so a fork refused as `carried_on` must not take the slot from the fork that counts; it is marked ineligible instead. Area entries, posted as the Run went, and Keepsakes, credited at `bossDefeated`, are left as they are (`tracker.finish` only keeps the payload for the results screen).
- Out of scope: Fluff arithmetic on the server; migrating Runs ended before the ledger (their tombstones stay); Keepsake credits.

## Implementation notes

The client (src/meta) follows the spec above, with these small additions, none of which change a rule:

- **Who hands a saved copy to its creditor.** `saveSuspendedRun`, `storePausedRun` and `abandonSuspendedRun` take a `QuitCreditor` (`creditQuit(snapshot)`) instead of `MetaProgress`: `MetaProgress.creditQuit` credits at once (signed out), `AccountRuns.creditQuit` claims an Account copy with its tag's leases (or the page's, for the Run it plays). The snapshot's tag is what tells the two apart, so passing the snapshot rather than its stats keeps the lease out of `MetaProgress`.
- **`runEnded` carries `runKey`.** `awardRun` is keyed by it, so the event is the one place it comes from.
- **The sweep also follows a lost upload answer.** The spec runs it after the *claim* queue drains following a network error; the saved Run queue does the same, since a lost answer to a replace is the case the sweep exists for (race 1b in the tests). Both are cheap: one `GET` of 20 rows.
- **A refused claim** fires `fluffAwarded` with `pending: false, amount: 0`; the results screen then reads "Not added: this Run carried on on another device." (`carriedOn`), "Already added on another device." (`elsewhere`) or "Not added: something went wrong on this side." (`rejected`). A credit the copy already held (`already`) fires it with the row's Fluff (`CreditOutcome.fluff`) and no award. `AccountRuns.creditOf(runKey)` (`credited` with the award, or with `award: null` for `already` / `pending` / `refused` with `why`) is what the results screen renders from, since it may open before or after the `runEnded` listener that credits; `AccountRuns.deferred(runKey)` (pending, with a claim of this page's out) is what the leaderboard posting waits on, and every outcome ends that wait: the entry posts unless the Run carried on elsewhere.
- **A pre-ledger cloud row** (no `creditedRuns`) adopted into a device keeps the device's set rather than wiping it (missing means unknown); when it is another Account's save being loaded (`replace`), the set starts empty.
- **Any copy applies any row.** A device that lost a Run to another device still applies that Run's ledger row to its own copy at the next sweep (one credit per copy, the key alongside the Fluff); the cloud save's whole-copy merge keeps one of them. The tests state this where it shows.
